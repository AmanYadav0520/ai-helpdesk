# CLAUDE.md

Guidance for Claude Code when working in this repository.

## Project Instructions

This project follows Code with Mosh's architecture and coding style.

- Follow Code with Mosh's folder structure.
- Don't refactor existing architecture unless explicitly asked.
- Prefer consistency with the course over new patterns.
- Explain how a suggestion differs from the course before proposing it.
- **Testing strategy**: default to a [component test](#component-tests) for a component/page's own logic (rendering, form validation, mutation payloads, loading/error states) — reach for a Playwright E2E test only for what a component test can't reach: real cross-request/backend behavior (e.g. the inbound-email webhook's DB threading logic, or `PATCH /api/tickets/:id`'s `assignedToId` DB-lookup validation), auth/session flows (real cookies, DB-backed session revocation/expiry/tampering), or a multi-page journey. When both could plausibly cover something, prefer the component test. See `e2e/tests/tickets.spec.ts` + `apps/web/src/pages/TicketsTable.test.tsx`/`apps/web/src/components/{TicketDetail,UpdateTicket,ReplyThread,ReplyForm}.test.tsx` for the precedent: list/detail rendering, status/category/assignee updates, and reply submission moved to component tests, leaving only the webhook's ticket-creation/threading behavior and its auth/validation failure paths in e2e.
- **Prune e2e coverage whenever component coverage catches up to it.** E2E tests accrete before a page/component has its own test file (or before a specific piece of its logic gets covered); once a component test asserts the same behavior a mocked API client, no real backend needed a matching e2e test becomes redundant weight (slower, DB-order-dependent, harder to debug) and should be deleted, not kept "just in case." Concretely: whenever you add or extend a component test, check whether it now duplicates an existing e2e test's assertion and remove the e2e test if so. Conversely, if you're about to delete an e2e test that covers logic with *no* component-test equivalent yet, write the component test first (see `apps/web/src/pages/LoginPage.test.tsx`, added specifically to backfill `LoginPage.tsx`'s client-side validation/loading/error-state logic before trimming `e2e/tests/auth.spec.ts` down to just what needs a real backend/session/browser) — never delete coverage and leave a gap. A test belongs in e2e only if it exercises something a mocked component test structurally cannot: a real HTTP round-trip to Postgres, real session cookies/CORS headers, or multi-page navigation. Don't keep an e2e test just because it's already written, and don't keep one to double-check a guarantee the framework/library already provides (e.g. React never executes markup from a controlled input's value — that's not app logic worth its own browser test).
- Use the `e2e-test-writer` subagent to write or update Playwright E2E tests.

## Architecture

Bun workspace monorepo with two independently deployable apps plus a shared `core` package — not a single Next.js app (see `tech-stack.md` for the revision note).

- **`core`** (top-level, sibling of `apps/`, matching the course's own layout) — no direct dependencies of its own, just a `zod` peer dependency; holds code shared between `apps/web` and `apps/server` (`core/schemas/`, see [Validation](#validation); `core/constants/`, see [Role](#authentication)). Not deployed on its own; both apps depend on it via `"core": "workspace:*"`.
- **`apps/server`** — Express v5 run directly by Bun, port 3001. CORS restricted to `WEB_ORIGIN` (default `http://localhost:3000`).
- Express 5 automatically forwards rejected promises from `async` route handlers to the error-handling middleware — don't wrap route bodies in `try`/`catch` just to catch-and-rethrow (see `POST /api/users` in `apps/server/src/routes/users.ts`). Only reach for `try`/`catch` in a handler when you need to do something with the error yourself (map it to a specific response, log it, etc.) — e.g. `GET /api/health` catches to return a deliberate `503` body instead of the default error response.
- Route modules live under `apps/server/src/routes/` (e.g. `routes/users.ts`), each exporting a default `Router()` mounted in `index.ts` via `app.use("/api/<name>", router)` — `requireAuth`/`requireAdmin` stay in their existing flat locations, not moved into a `middleware/` subfolder.
- Background jobs run on `pg-boss` (`apps/server/src/lib/queue.ts`), reusing `DATABASE_URL` — no separate queue infra. `index.ts` wraps startup in an async `boot()` that awaits `startQueue()` before `app.listen`, and stops the queue gracefully on `SIGTERM`/`SIGINT`. Ticket classification is the only job registered so far (`sendClassifyJob`, enqueued non-blocking from `POST /api/webhooks/inbound-email` after the `201` response); the worker itself (`boss.work(...)`) lives in the same file as `startQueue`/`sendClassifyJob`, matching the course's own `queue.ts`, rather than a separate module per job.
- **`apps/web`** — React 19 + Vite, port 3000. Tailwind via `@tailwindcss/vite`.
- In dev, the apps talk over plain cross-origin HTTP (different ports, no proxy). **In production they're proxied to look same-origin**: `apps/web/vercel.json` rewrites `/api/*` to the Railway API before the SPA catch-all, so the browser only ever talks to the Vercel domain and the Better Auth session cookie is first-party (`SameSite=Lax`, set automatically `Secure` since `BETTER_AUTH_URL` is `https://`). This was added because Safari/iOS unconditionally blocks cross-site cookies (no `SameSite=None`/`Partitioned` combination gets around it — CHIPS isn't supported there) — a same-origin proxy is the only fix that works on every browser. `VITE_API_URL` is unset in Vercel production so `apps/web/src/lib/api.ts`/`auth-client.ts` fall back to relative URLs and go through the rewrite; it's still used for local dev (`http://localhost:3001`) where the two ports count as same-site anyway.
- Client env vars need a `VITE_*` prefix (e.g. `VITE_API_URL`) to be exposed via `import.meta.env`.
- Sessions are database-backed, not JWT, so an admin can instantly revoke an agent's active sessions.

## Data Fetching

- Use axios through `apps/web/src/lib/api.ts`; don't create per-component axios instances.
- Use TanStack Query (`useQuery`/`useMutation`) for server state instead of `useEffect` + manual fetching.
- **Table components own their query**: a resource table (e.g. `apps/web/src/pages/UsersTable.tsx`) calls its own `useQuery` internally rather than receiving `data`/`isPending` as props from its page — the page (`UsersPage.tsx`) just renders `<UsersTable />` with no data-fetching logic of its own. Matches the course's `UsersTable`/`UsersPage` split. Loading-skeleton rows and the fetch-error `Alert` live inside the table component too, for the same reason.

## Validation

Use zod for data validation, both client and server side — don't hand-roll validation logic.

- **Shared schemas**: any schema needed by both `apps/web` and `apps/server` (e.g. create/update payloads for a resource) belongs in the `core` workspace, not duplicated in each app. Define it under `core/schemas/<resource>.ts` (zod v4 syntax, e.g. `z.email(...)`) and export both the schema and its inferred type (`z.infer<typeof schema>`) — see `core/schemas/users.ts`. Import it with a bare `core/schemas/<resource>` specifier (mapped via `core/package.json`'s `exports` field — subpaths there include an explicit `.ts` extension so `tsc`'s exports resolution finds the file; Bun/Vite resolve it either way). Both `apps/web` and `apps/server` depend on `core` via `"core": "workspace:*"` and on `zod` directly (`^4`, satisfying `core`'s `zod` peer dependency) — one zod major version across the whole repo, no more per-app version split. A schema used by only one side (e.g. `Login.tsx`'s sign-in form, which Better Auth handles, not a shared resource payload) stays local to that app — don't move something into `core` just because it uses zod.
- **Client**: React Hook Form is the form library — wire the (often `core`-provided) schema to the form via `@hookform/resolvers`' `zodResolver`, and render fields with `Controller` (not `register`), matching the `Field`/`FieldLabel`/`FieldError` shadcn pattern (see `apps/web/src/pages/LoginPage.tsx`, `apps/web/src/pages/UserForm.tsx`).
- **Create/edit form pattern**: one form component handles both, taking an optional resource prop (e.g. `UserForm`'s `user?: { id, name, email }`) — `const isEdit = !!user` switches the zod schema/resolver, the mutation's HTTP method + URL, and the submit button's label. `defaultValues` fall back to `""` per field when there's no resource (create), or the resource's own values when editing. This is `UserForm.tsx`'s actual course name — it started as `CreateUserForm.tsx` (create-only) and was renamed once edit support was added, matching the course's own lesson progression exactly.
- **Optional-password-on-edit**: an update schema's `password` field is `z.union([z.literal(""), z.string().trim().min(8, "...")])` — a blank password is valid and means "don't change it"; anything else must meet the same minimum as create. The server only touches the `Account` password row when `password` is truthy (see `PUT /api/users/:id` in `apps/server/src/routes/users.ts`); the client always sends the field (even as `""`) rather than omitting it, since the schema requires it.
- **Form vs. dialog split**: keep the `<form>` itself (fields, `useForm`, the mutation, an `onSuccess` callback prop) in its own component, separate from whatever owns the `Dialog`/open state. For a resource with both create and edit, the course puts the `Dialog`/`DialogTrigger`/`DialogContent` chrome directly in the page component (not a separate wrapper component per mode) — the page holds a `DialogState = { mode: "create" } | { mode: "edit"; user } | null`, one `Button` opens it in create mode, each row's edit action opens it in edit mode, and a single `Dialog` renders `<UserForm user={...} onSuccess={...} />` with the title switched on `dialog?.mode`. See `apps/web/src/pages/UsersPage.tsx`. (An earlier, create-only version of this feature had a standalone `CreateUserDialog.tsx` wrapper component; it was deleted once edit was added, to avoid two near-duplicate dialog wrappers — don't recreate it.) Relies on Radix `Dialog.Content` unmounting when closed (no `forceMount` used anywhere in this repo) to reset the form's internal state between opens — don't add manual `reset()` calls to work around a problem that doesn't exist.
- **Destructive-action confirmation**: use the shadcn `alert-dialog` component (`apps/web/src/components/ui/alert-dialog.tsx`, added via `bunx shadcn@latest add alert-dialog -y` — same `nova` preset as `dialog.tsx`), not the plain `Dialog`, for anything requiring an "are you sure?" step (e.g. deleting a user). It gets its own state variable, separate from the create/edit `DialogState` above — see `deletingUser` alongside `dialog` in `apps/web/src/pages/UsersPage.tsx` — because it's a structurally different Radix root/component, not a duplicate tracker of the same thing. `AlertDialogAction`/`AlertDialogCancel` drive the confirm/cancel buttons; `onOpenChange` clears the state on any close (Cancel, Escape, outside click).
- **Server**: `validate(schema, req.body, res)` (`apps/server/src/lib/validate.ts`) in the route handler — `const data = validate(schema, req.body, res); if (!data) return;`. Matches the course's own `validate()` helper (`server/src/lib/validate.ts`) rather than inlining `schema.safeParse(...)` + the `400`/first-issue-message check per handler; adopted after that inline version was duplicated verbatim across `POST` and `PUT /api/users/:id` in `apps/server/src/routes/users.ts`. An update's email-uniqueness check excludes the record being edited (`existing && existing.id !== id`), unlike create's unconditional check — otherwise saving a user without changing their email would falsely 409 against themselves.
- **Reusable route-handler helpers belong in `apps/server/src/lib/`, not inline in the route file.** `validate()` above is the original example; `parseFromField`/`stripSubjectPrefixes` (`apps/server/src/lib/parse-inbound-email.ts`, used by `POST /api/webhooks/inbound-email` in `apps/server/src/routes/webhooks.ts` to turn a raw `"Name <email>"` header and a `Re:`/`Fwd:`-prefixed subject into clean fields) is the second. Write parsing/formatting logic a route handler needs as a named export in `lib/`, not as a private function defined inside the route module, even on its first use — so a second route that needs the same logic imports it instead of redefining it.
- **Soft delete**: `User.deletedAt DateTime?` (nullable) — `DELETE /api/users/:id` never removes a row; it sets `deletedAt` to now and deletes that user's `Session` rows (`prisma.session.deleteMany`) to force out any active logins immediately, since a soft delete doesn't cascade like a real delete would. It 404s if the id doesn't exist and 403s with `{ error: "Admin users cannot be deleted" }` if the target's role is `Role.admin` — this repo never creates a second admin, so in practice that protects the sole bootstrap admin. `GET /api/users` filters `where: { deletedAt: null }` so deleted users disappear from the list. `requireAuth` (`apps/server/src/require-auth.ts`) additionally 401s if `session.user.deletedAt` is set — belt-and-suspenders alongside the explicit session deletion, for any request that's already in flight when a user is deleted. It also unassigns that user's tickets (`prisma.ticket.updateMany({ where: { assignedToId: id }, data: { assignedToId: null } })`) — `Ticket.assignedTo`'s `onDelete: SetNull` in `schema.prisma` is a real foreign-key action that only fires on an actual row delete, and a soft delete never triggers it, so without this explicit step tickets would stay assigned to a deleted agent forever.

## Authentication

Better Auth (`apps/server/src/auth.ts`), backed by Postgres via `prismaAdapter`. See `tech-stack.md` for rationale (why Better Auth, why database sessions).

- **Mounting**: `app.all("/api/auth/*splat", toNodeHandler(auth))` runs *before* `express.json()`, since Better Auth parses its own request body. Don't add body-parsing middleware ahead of it.

- **Sign-up**: email/password only, `disableSignUp: true` — no self-registration through Better Auth. The bootstrap admin comes from `bun run seed` (`apps/server/prisma/seed.ts`), which creates one admin from `ADMIN_EMAIL`/`ADMIN_PASSWORD`/`ADMIN_NAME` (skips if that email exists). Beyond that, an admin creates agent accounts directly via `POST /api/users` (`apps/server/src/routes/users.ts`), which writes the `User`/`Account` rows itself rather than going through Better Auth's (disabled) sign-up flow.

- **Role**: `admin` | `agent` (default `agent`), defined via Better Auth's `additionalFields` (`input: false`, so clients can't set it). **Always use the `Role` enum from `core/constants/role.ts` (`Role.admin` / `Role.agent`, a native TS `enum`) instead of hardcoded `"admin"`/`"agent"` string literals — in both app code and tests, client and server.** Both apps import it (`import { Role } from "core/constants/role"`) rather than each defining their own — `apps/server/src/require-admin.ts`, `apps/server/src/routes/users.ts`, `apps/server/src/routes/agents.ts`, `apps/server/src/routes/tickets.ts`, `apps/server/src/auth.ts` (its `additionalFields.role.defaultValue`), `apps/web/src/components/AdminRoute.tsx`, `apps/web/src/components/NavBar.tsx`, and `apps/web/src/pages/UsersTable.tsx` all compare against `Role.admin`/`Role.agent`, never a raw string literal — and so do the component tests that build mock user data or assert on rendered role text (`UsersTable.test.tsx`, `UserForm.test.tsx`, `UsersPage.test.tsx`). Trust `req.user.role` server-side only — never the client. The one exception is `apps/server/src/auth.ts`'s `additionalFields.role.type: ["admin", "agent"]`, which stays plain strings because that's Better Auth's own API surface. `apps/server/prisma/seed.ts` is also an exception — it still imports `Role` from the Prisma-generated client (`../src/generated/prisma/enums`), matching the course's own seed script, which never switched to the `core` constant either. **`Role` was originally a plain `as const` object matching the course's own `core/constants/role.ts` exactly; converted to a native `enum` (deliberate divergence from the course) for consistency with `TicketStatus`/`TicketCategory`/`SenderType` (`core/constants/ticket-status.ts`/`ticket-category.ts`/`sender-type.ts`), which use native `enum`s because `z.enum()` in `core/schemas/tickets.ts` and the ticket-UI `Select` dropdowns (`Object.values(TicketStatus)`, etc.) both work directly off them. TS string-enum members are structurally assignable to Prisma's generated literal-union enum types one-directionally (verified), so this doesn't break Prisma interop anywhere `Role`/`TicketStatus`/etc. flow into a `prisma.*` call.**

- **Protecting routes**: use the `requireAuth` middleware (`apps/server/src/require-auth.ts`) — 401s without a session, otherwise attaches `req.user`/`req.session`. Applied per-route; nothing is protected by default.

- **Client**: `apps/web/src/lib/auth-client.ts` wraps `better-auth/react` (`authClient`, `useSession`, `signIn`, `signOut`). `ProtectedRoute.tsx` redirects to `/login` when there's no session.

- **Env vars**: server needs `DATABASE_URL`, `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`, `WEB_ORIGIN`; web needs `VITE_API_URL`. See `apps/server/.env.example`.
